# 服务端业务逻辑审查（2026-11-24，0.2.39 / 0.2.40）

用户的要求："代码写的是对的，但是不符合正常的逻辑"。这次不是找代码 bug，而是挑一个真实的人、一个真实的场景，从头走一遍，看他看到的东西对不对、能不能照着做。

范围是服务端：
- 第三方软件和老版本客户端用我们的订阅；
- 会员流程：开通 → 邀请 → 注册 → 用量 → 降速 → 加量 → 到期；
- 主服务器和子服务器的同步；
- 账期边界：每月重置、跨月、到期当天、时区；
- 升级、回滚、备份恢复、证书续期、端口占用；
- 面板和会员页上的每一句提示。

客户端那一半在客户端仓库。

严重程度：**高** = 用户会被骗、会白用或会断网；**中** = 提示和实际不符，用户照着做会走错；**低** = 措辞不准或少见的边角。

处理一栏：**已修**（测试在 `tests/test_logic_review.py`，L-01..L-08 在 0.2.39，L-09..L-12 在 0.2.40）/ **要修**（排到后面的版本）/ **不是问题**（写了理由）。

## 6. 从 legend 实际运维得到的启示（2026-11-24）

legend 是用户在用的另一套代理系统（一台主服务器加几台子服务器，Clash 和小火箭订阅），它和 vps2vpn 要解决的问题一样。2026-11-24 给它加了三台 Google Cloud 服务器，排查了「新加坡太慢」，搭了一个中转。下面是这次遇到的事和对 vps2vpn 的启示。**只记录，没改 vps2vpn 的代码。** 具体地址都去掉了；延迟用的是 Globalping 在中国移动（AS9808）、电信（AS4134）、联通（AS4837）测试点的结果，取中位数。

| # | 流程 | 场景 | 发生了什么 | 对 vps2vpn 应该怎样 | 严重程度 | 处理 |
|---|---|---|---|---|---|---|
| R-1 | 订阅线路顺序 | 一台新加坡服务器同时有 IPv4 和 IPv6 | 中国移动、联通走 **IPv4** 去这台机器时，被运营商的国际出口交给 Lumen，在**美国洛杉矶**转一圈再回新加坡，延迟 190–225 ms；走 **IPv6** 不绕路，只有 92–96 ms。服务器本身很闲，问题出在路由上，服务器这边调不了。同一次测试里，美国几台 IPv4 和 IPv6 差不多，悉尼反而 IPv4 更快（移动 169 对 279+ ms）。**所以不能一刀切，要按服务器、按实测来选。** legend 的处理：这台服务器的 fallback 组改成 IPv6 线路在前、IPv4 在后（没有 IPv6 的网络自动退回 IPv4），没有改成只走 IPv6（那样会让没有 IPv6 的人直接断网） | `subscription._ordered()` 现在**总是把 IPv4 放在 IPv6 前面**，会碰到同样的问题。建议：① 每台服务器加一个「优先 IPv6」开关（只调顺序，不删 IPv4）；② 部署工具 / `vps2vpn doctor` 加一项「国内三网 IPv4 / IPv6 延迟对比」，差得多时在面板提示「建议打开优先 IPv6」；③ 不提供「只用 IPv6」，或者藏进高级里并写明后果 | 中 | 要做 |
