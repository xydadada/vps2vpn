## 架构、数据流与重点不变量

服务端使用 Python 标准库的 HTTP/TLS 入口和共享 SQLite 连接；面板、周期任务、集群线程会同时读写同一份状态。用户凭据转换为 Xray/Hysteria/sing-box 的用户配置，同时转换为各类客户端订阅。流量从 core 采样与子节点累计游标进入用户用量，配额判断决定 enabled，再触发配置重载及节点同步。

这条链路最重要的约束是：**一次账户/计费决策的状态必须一起提交；网络响应重放不应再次计费；配置文件必须完整且语义有效；无法认证对端时不得先发送凭据；已经取消的连接意图不能被迟到回调重新执行。**

1. 数据事务使用 SAVEPOINT 支持嵌套。成员规则、流量写入、集群游标提交可以组合，而不会在外层事务中再次 BEGIN。Python RLock 保护整个共享连接的事务生命周期。
2. 集群网络请求放在数据库事务外；拿到并完整验证响应后，才进入短事务重读游标和落账。不能仅在内存更新 seen。
3. 邀请分享采用“已分配或已消费仍占用”的账本。10 GiB 父账号分享 9 GiB 后，子账号消费 9 GiB 再暂停，父账号仍只有 1 GiB 自用空间。暂停一个仅消费 2/5 GiB 的子账号可以回收未用的 3 GiB；不能返还已用的 2 GiB。
4. 删除邀请子账号时，已消费的份额以父账号 used_down 配额债保留，封顶原 grant；不再写入 daily traffic，避免全局历史二次计量。因此此类父账号 used_down 包含已转移的配额债，并非全部来自父账号自己的下行采样。这是保持现有 schema 的明确取舍。管理员删除中间邀请者仍沿用原有策略：直属下级脱离邀请关系成为独立账号；本轮仅保留已消费债务，不宣称仍向祖先保留这些独立账号的未用授权。普通成员不能删除账号。
5. 邀请子树计费改用显式栈与路径环检测，避免深链达到 Python 递归上限；按字节封顶再换算 GiB。专项测试覆盖 2500 层、活跃最末级、异常环和管理员删除中间账号的既有策略。周期 enforce 使用同一 DB 事务完成重置、快照和决策，按实际邀请关系后序处理；通知在事务提交后发送。
6. 文件写入采用同目录独立 staging、完整写入与原子替换。原子替换不等于跨文件配对事务，也不保证所有文件系统的掉电持久性。
7. 配额判断仍由服务器执行，网页和 Subscription-Userinfo 只是展示。客户端接管及故障上报由当前生命周期/订阅意图约束，未改 REST API 字段或 token 格式。

## 跨仓库兼容性

配套客户端沿“订阅导入→安全保存→Go 解析/增强→配置持久化→Helper/Core→系统代理→面板状态/报告”追踪，报告分别为客户端 PR 中的 AUDIT_CORE_2026-11-20.md 与 AUDIT_APP_2026-11-20.md。

- 仍使用 /s/<token>/api/me 和 api/report，认证 header、token 字符表、JSON 字段、protocol 标签保持兼容。Content-Length 与合法 chunked 均可被服务端接受。
- cluster 的完整 users snapshot 要求是有意收紧：缺失 users/坏行会拒绝整批，旧主节点已绑定时还必须提供 master_id。现有本项目客户端/主节点 payload 有该字段；未知第三方调用方需遵守完整快照契约。
- 订阅名去重是确定性的，但既有冲突或非法字符名称会变化，客户端保存的手选节点可能需要重选。
- 共享配额更正后，旧版本曾透支的账户可能被正确暂停。应核对邀请额度和已用量，不要通过清零用量掩盖超发。
- 恢复备份会清除旧会话，需要使用备份里的管理员凭据/面板路径重新登录。修改会员密码会使其他会话失效。
- Telegram 从群组绑定迁移为私聊；SSH known_hosts 开始持久化，合法重装换钥需核实后更新记录。
- 基线三种 core 与客户端内核 pin 没有盲目升级。认证链的严格校验可能使此前不可信连接失败，这是必要的行为变化。

## 剩余风险与后续优先级

1. **高：HTTP 订阅引导。** 自签兼容 URL 仍可使用 HTTP，token、用户协议密码、路由规则都可能被链路读取或修改。本轮没有单方面切断现有第三方客户端，也没有用 skip-verify 冒充认证。优先部署公开可信证书；完整修复需要 pin/CA 带外交付、轮换、存量链接迁移及各客户端验证。HTTP 安装包 URL 同样不具备传输认证。
2. **高：最终验证与上游并发。** 配套客户端 race 检查已发现锁定 Clash.Meta 的 route server 生命周期竞争，见客户端最终报告。不能以普通功能测试通过宣称该依赖没有并发风险；不跳过 race 或加 sleep 制造绿灯。
3. **计费边界。** TUIC API 缺少稳定原生 per-user 累计计数，短连接采样归属仍近似；进程重启 epoch、用户清零、月重置和多节点延迟的严格账期边界尚需协议级方案。不能用于未经进一步验证的精确账单。Subscription-Userinfo 仍报告原 quota_gb，邀请用户的实际可用额应以成员 API 为准。max_ips/devices 混合源 IP 去重与 Hysteria 客户端数，同设备跨协议可能重复、NAT 可合并多设备，属于启发式连接限制，不能宣称精确物理设备数。
4. **事务与导入范围。** 本轮保护当前共享连接及主要组合写入；不是所有管理员操作/CLI/多进程配置文件操作的全局串行化。备份是管理员导入的全权限数据，已校验结构和列但没有为每个 settings/历史字段补完整版本化 schema。异常/恶意备份的所有业务语义仍需更严格校验。
5. **复杂邀请数据与性能。** 深链递归限制已通过显式栈消除；enforce 不再依赖用户 ID 的先后顺序。大用户量重复扫描仍需 profiler 与统一账本快照，跨级周期修改仍需更完整账期策略。管理员删除中间账号会把直属下级转为独立账号，属于原有管理员授权语义；若业务需要保留整棵授权树，应另行设计转移/回收规则。没有宣称共享模型已覆盖所有异常历史数据。
6. **部署/持久性边界。** 安装回滚只恢复面板代码并尽力重载，不是 core binary、DB、系统配置、内核和 swap 的整体回滚。证书 key/cert 两文件仍有替换窗口；core apply 的 RLock 只对单一进程有效；并行 CLI/daemon 需要系统锁或单一控制入口。
7. **信任与供应链。** 首次 SSH 仍是 TOFU；默认面板安装源为 mutable branch；下载与 checksum 同源不等于独立签名。建议不可变发布、签名/证明、最小云防火墙、专用服务权限和定期恢复演练。
8. **网络与性能。** DNS rebinding、IPv6/UDP 私网 ACL、真实证书轮换、路由/故障恢复仍需 pinned core E2E 和真实链路测试。监控/AI 匿名探测无法保证账号级服务可用，系统 getaddrinfo 不受 socket timeout 严格约束。
9. **后续审计覆盖。** 继续客户端继承 UI、平台启动/自动更新、特权安装目录权限与 IPC server/outbox 全量阅读；先修复可复现问题，再测性能，避免无收益改动。
